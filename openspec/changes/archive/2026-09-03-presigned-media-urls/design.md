## Context

Character and image GET endpoints currently return raw R2 storage keys in their responses. These keys are internal identifiers — not accessible URLs — so the frontend cannot use them to display media. Presigned GET URLs are time-limited signed URLs generated by the backend that allow direct access to private R2 objects.

The `r2Storage` implementation already has `GeneratePresignedGetURL` implemented with full tracing and metrics. The `StorageService` interface used by usecases does not expose it, and no handler currently performs presigning.

## Goals / Non-Goals

**Goals:**
- Replace raw R2 paths in character and image GET responses with presigned GET URLs (1hr TTL)
- Remove the original image R2 path from list responses entirely
- Add a new endpoint to list images associated with a character
- Keep presigning logic out of the usecase layer

**Non-Goals:**
- Caching or reusing presigned URLs across requests
- Changing how R2 paths are stored in the database
- Modifying write flows (upload, avatar upload, thumbnail generation)
- Pagination on the character images endpoint

## Decisions

### Presigning at the handler layer via a shared `Presigner` interface

**Decision:** Presigning happens in the handler layer. A `Presigner` interface is declared once in the handler package. Both `CharacterHandler` and `ImageHandler` receive a `Presigner` dependency and call it before building their JSON responses.

**Alternatives considered:**
- *Usecase layer presigning with view DTOs:* Would require new return types from usecases (e.g. `CharacterView`, `ImageView`) to carry presigned URLs alongside domain data. Adds a layer of types for what is essentially a presentation concern.
- *Handler receives `StorageService` directly:* `StorageService` includes `DeleteObject` and `GeneratePresignedPutURL`, which are never needed in a handler. Violates the principle of narrow dependencies.

**Rationale:** Presigning is a uniform, presentation-layer concern — every handler that needs it needs exactly the same thing. A shared interface in the handler package is the right scope: it avoids duplicating an identical interface per handler while keeping the dependency narrow and test-friendly. The pattern is consistent with how `Transactor` is shared across usecases without being redefined per-usecase.

```go
// handler/presign.go
type Presigner interface {
    GeneratePresignedGetURL(ctx context.Context, key string, ttl time.Duration) (string, error)
}
```

`r2Storage` already satisfies this interface without any changes to the storage implementation.

### 1-hour TTL for all presigned GET URLs

**Decision:** All presigned GET URLs generated by this change use a 1-hour TTL.

**Rationale:** Upload presign TTL (`PresignTTL`) is 15 minutes and is intentionally short since it authorizes a write. Read URLs have no write risk and a longer TTL reduces presigning frequency if the frontend caches responses. A new constant (`PresignGetTTL = 1 * time.Hour`) is added alongside the existing one.

### New `ListByCharacterID` repository method

**Decision:** A new method is added to `ImageRepository` to fetch images by character association:

```go
ListByCharacterID(ctx context.Context, characterID uuid.UUID, userID uuid.UUID) ([]*domain.Image, error)
```

This queries `images` joined via `image_characters` filtered by both `character_id` and `user_id`. The `userID` filter is applied on `images.user_id` to enforce ownership without requiring a separate character ownership check.

**Rationale:** A raw SQL join is simpler and more efficient than loading the character with its associations via GORM's preload. The character ownership is implicitly enforced: if the character doesn't exist or belongs to another user, no images will match, and the response will be an empty array — which is correct behavior.

> Note: This means the endpoint does not 404 when the character ID is invalid or belongs to another user — it returns an empty array. This is acceptable for a listing endpoint.

### No change to usecase return types

**Decision:** `characterUsecase` and `imageUsecase` continue to return domain types (`*domain.Character`, `*domain.Image`). Presigning is handled in the handler after the usecase returns.

**Rationale:** Presigned URLs are not business logic. The usecase layer deals with ownership enforcement and data retrieval; the handler layer is responsible for shaping the response for the client, which includes generating display URLs.

## Risks / Trade-offs

**N presign calls per list request** → Presigning is pure HMAC signing (no network round trip to R2). For a user with many images, this adds negligible latency. Not a concern at current scale.

**Presigned URLs expire after 1 hour** → If the frontend caches a response and attempts to render an image after expiry, it will get a 403 from R2. This is expected behavior for presigned URLs. The frontend should treat the URL as short-lived and re-fetch the resource if expired.

**Nil thumbnails on character images endpoint** → Many images may not have a thumbnail yet (worker hasn't processed them). `thumbnail_url` is null in these cases — the frontend must handle this.
