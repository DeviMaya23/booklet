## ADDED Requirements

### Requirement: User is identified internally by an app-owned UUID
The system SHALL assign each user a UUID generated by the application at provisioning time. This UUID SHALL be the primary key used for all internal database relationships. The IdP-issued subject (`idp_subject`) SHALL be stored as a separate column and used only for IdP API calls and cross-system communication with bookleaf.

#### Scenario: New user provisioned for the first time
- **WHEN** a JWT with a previously unseen `sub` claim is validated
- **THEN** the system creates a new user row with a freshly generated UUID as `id` and the JWT `sub` stored as `idp_subject`

#### Scenario: Returning user is found by idp_subject
- **WHEN** a JWT with a previously seen `sub` claim is validated
- **THEN** the system retrieves the existing user row by matching `idp_subject` and returns the app UUID as the user's identity

### Requirement: App UUID is the identity token flowing through all internal layers
All internal layers (usecase, repository, domain) SHALL use the app UUID (`uuid.UUID`) as the user identity type. No layer below the auth middleware SHALL receive or store the raw Kinde subject as a user identifier, except where explicitly passing it to an external system.

#### Scenario: Handler receives user identity from context
- **WHEN** an authenticated request reaches a handler
- **THEN** the user identity extracted from context is a `uuid.UUID`, not a string

### Requirement: idp_subject is available in context for cross-system calls
The system SHALL store the authenticated user's `idp_subject` in the Echo context alongside the app UUID, so handlers that need to call bookleaf can retrieve it without an additional database lookup.

#### Scenario: Handler retrieves idp_subject for a bookleaf call
- **WHEN** a handler needs to call a bookleaf endpoint that requires the Kinde subject
- **THEN** the handler retrieves the `idp_subject` directly from the Echo context
