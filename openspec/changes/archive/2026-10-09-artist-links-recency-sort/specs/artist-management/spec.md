## MODIFIED Requirements

### Requirement: Artist data model
The `artists` table SHALL use the following schema:
- `id` — PostgreSQL `uuid` type, primary key, generated by the application
- `user_id` — `uuid`, foreign key referencing `users(id)`, not null
- `name` — `text`, not null
- `notes` — `text`, nullable
- `last_used_at` — `timestamptz`, nullable
- `created_at` — `timestamptz`, not null
- `updated_at` — `timestamptz`, not null

A composite unique constraint `UNIQUE(user_id, name)` SHALL be enforced at the database level. Different users may register an artist with the same name; the same user may not.

#### Scenario: Artist ID is a native UUID column
- **WHEN** an artist is persisted to the database
- **THEN** the `id` column is of PostgreSQL `uuid` type and contains a valid UUID value

#### Scenario: Duplicate name rejected for same user
- **WHEN** a user attempts to create an artist with a name they already have registered
- **THEN** the database rejects the insert with a unique constraint violation

#### Scenario: Same name allowed for different users
- **WHEN** user A and user B both create an artist with the same name
- **THEN** both rows are inserted successfully

### Requirement: Create artist
An authenticated user SHALL be able to create an artist by providing a name. Notes and links are optional. The system SHALL return 201 with the created artist on success.

Request body fields:
- `name` — required, non-empty string
- `notes` — optional string
- `links` — optional array of link objects; each element requires `url` (valid URL) and `is_primary` (boolean)

#### Scenario: Successful creation
- **WHEN** an authenticated user sends `POST /artists` with a valid `name`
- **THEN** the system returns 201 with the created artist object

#### Scenario: Missing name
- **WHEN** an authenticated user sends `POST /artists` without `name`
- **THEN** the system returns 422

#### Scenario: Duplicate name for same user
- **WHEN** an authenticated user sends `POST /artists` with a name they already have registered
- **THEN** the system returns 409

#### Scenario: Invalid URL in links
- **WHEN** an authenticated user sends `POST /artists` with a `links` element whose `url` is not a valid URL
- **THEN** the system returns 422

#### Scenario: Malformed request body
- **WHEN** an authenticated user sends `POST /artists` with invalid JSON
- **THEN** the system returns 400

---

### Requirement: List artists
An authenticated user SHALL be able to retrieve artists they own, ordered by `last_used_at DESC NULLS LAST, name ASC`. The endpoint SHALL accept an optional `q` query parameter for freetext name filtering; when absent, all artists owned by the user are returned.

Optional query parameters:
- `q` — freetext substring search against `name` (case-insensitive); absent means no filter

#### Scenario: Successful listing with no filters
- **WHEN** an authenticated user sends `GET /artists`
- **THEN** the system returns 200 with an array of artist objects (may be empty), ordered by `last_used_at DESC NULLS LAST, name ASC`

#### Scenario: Only owner's artists returned
- **WHEN** multiple users have artists and user A sends `GET /artists`
- **THEN** the response contains only user A's artists

#### Scenario: Filter by q returns matching artists
- **WHEN** an authenticated user sends `GET /artists?q=jane`
- **THEN** the system returns only artists whose name contains "jane" case-insensitively, in recency order

---

### Requirement: Update artist
An authenticated user SHALL be able to fully replace the editable fields of an artist they own using PUT semantics. The request body SHALL always include all updatable fields; the server SHALL write them exactly as received.

Updatable fields: `name`, `notes`, `links`.

- `name` — required, non-empty string
- `notes` — nullable string; `null` clears the value
- `links` — array of link objects (may be empty); replaces all existing links

#### Scenario: Successful update
- **WHEN** an authenticated user sends `PUT /artists/:id` with all updatable fields
- **THEN** the system returns 200 with the updated artist reflecting the submitted values

#### Scenario: Clearing notes
- **WHEN** an authenticated user sends `PUT /artists/:id` with `"notes": null`
- **THEN** the system returns 200 and the artist's `notes` is null

#### Scenario: Clearing all links
- **WHEN** an authenticated user sends `PUT /artists/:id` with `"links": []`
- **THEN** the system returns 200 and the artist's `links` array is empty

#### Scenario: Duplicate name on update
- **WHEN** an authenticated user sends `PUT /artists/:id` with a name already used by another artist they own
- **THEN** the system returns 409

#### Scenario: Artist not found or not owned
- **WHEN** an authenticated user sends `PUT /artists/:id` for an artist that does not exist or belongs to another user
- **THEN** the system returns 404

#### Scenario: Invalid URL in links on update
- **WHEN** an authenticated user sends `PUT /artists/:id` with a `links` element whose `url` is not a valid URL
- **THEN** the system returns 422

#### Scenario: Malformed request body
- **WHEN** an authenticated user sends `PUT /artists/:id` with invalid JSON
- **THEN** the system returns 400

---

### Requirement: Artist response shape
Every artist response SHALL use snake_case field names and include the following fields:
- `id` (string, UUID)
- `name` (string)
- `notes` (string or null)
- `links` (array of objects, each with `id` string, `url` string, `is_primary` boolean)
- `created_at` (string, RFC3339)
- `updated_at` (string, RFC3339)

#### Scenario: Response uses snake_case keys
- **WHEN** the system returns an artist response
- **THEN** all JSON keys are in snake_case format

#### Scenario: Links array present even when empty
- **WHEN** an artist has no links
- **THEN** the response SHALL include `"links": []` rather than omitting the field
