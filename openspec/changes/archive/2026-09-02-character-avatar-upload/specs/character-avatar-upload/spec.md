## ADDED Requirements

### Requirement: pending_character_avatar_uploads data model
The `pending_character_avatar_uploads` table SHALL use the following schema:
- `id` — `uuid`, primary key, generated by the application
- `user_id` — `uuid`, foreign key referencing `users(id)`, not null
- `character_id` — `uuid`, foreign key referencing `characters(id)` with `ON DELETE CASCADE`, not null
- `r2_key` — `text`, not null — the R2 object key generated at init time
- `mime_type` — `text`, not null
- `created_at` — `timestamptz`, not null

#### Scenario: Pending row is created on init
- **WHEN** a valid `POST /characters/:id/avatar/init` request is processed
- **THEN** a row is inserted into `pending_character_avatar_uploads` with the character's id, the authenticated user's id, the generated R2 key, and the provided mime_type

#### Scenario: Pending row is deleted on complete
- **WHEN** `POST /characters/:id/avatar/:uploadID/complete` succeeds
- **THEN** the `pending_character_avatar_uploads` row with that uploadID is no longer present in the table

#### Scenario: Pending row is cascade-deleted when character is deleted
- **WHEN** a character with an in-flight pending avatar upload is deleted
- **THEN** the corresponding `pending_character_avatar_uploads` row is deleted by the database via cascade

---

### Requirement: Init avatar upload
An authenticated user SHALL be able to initiate an avatar upload for a character they own. The system SHALL verify character ownership, create a `pending_character_avatar_uploads` record, generate an R2 object key (`{userID}/files/{uuid}`), and return a presigned PUT URL valid for 15 minutes.

Request body fields:
- `mime_type` — required; must be one of: `image/jpeg`, `image/png`

Response body:
- `id` — the pending upload UUID (used as `:uploadID` in the complete endpoint)
- `upload_url` — the presigned R2 PUT URL
- `expires_at` — RFC3339 timestamp when the presigned URL expires

#### Scenario: Successful init
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/init` with a valid mime_type for a character they own
- **THEN** the system returns 201 with `id`, `upload_url`, and `expires_at`; a `pending_character_avatar_uploads` row exists in the database

#### Scenario: Character not found or not owned
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/init` for a character that does not exist or belongs to another user
- **THEN** the system returns 404

#### Scenario: Invalid character UUID path param
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/init` with a non-UUID `:id`
- **THEN** the system returns 400

#### Scenario: Missing mime_type
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/init` without `mime_type`
- **THEN** the system returns 422

#### Scenario: Unsupported mime_type
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/init` with a mime_type not in the allowed set
- **THEN** the system returns 422

### Requirement: Complete avatar upload
An authenticated user SHALL be able to complete an avatar upload by confirming a pending upload. The system SHALL:
1. Read the character's current `avatar_r2_path` (snapshot it)
2. Update `characters.avatar_r2_path` to the new R2 key
3. Delete the previous R2 object if one existed
4. Delete the `pending_character_avatar_uploads` row

The character update and pending row deletion SHALL occur within a single transaction. R2 deletion of the old object happens after the transaction commits.

#### Scenario: Successful complete with no previous avatar
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/:uploadID/complete` and the character has no existing avatar
- **THEN** the system returns 204 and `characters.avatar_r2_path` is set to the new R2 key

#### Scenario: Successful complete replacing an existing avatar
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/:uploadID/complete` and the character already has an `avatar_r2_path`
- **THEN** the system returns 204, `avatar_r2_path` is updated to the new key, and the previous R2 object is deleted from storage

#### Scenario: Pending upload not found or not owned
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/:uploadID/complete` for a pending upload that does not exist or belongs to another user
- **THEN** the system returns 404

#### Scenario: Invalid uploadID path param
- **WHEN** an authenticated user sends `POST /characters/:id/avatar/:uploadID/complete` with a non-UUID `:uploadID`
- **THEN** the system returns 400

---

### Requirement: Delete avatar
An authenticated user SHALL be able to clear their character's avatar via `DELETE /characters/:id/avatar`. The system SHALL:
1. Look up the character (verify ownership)
2. If `avatar_r2_path` is null, return 204 immediately (idempotent)
3. Set `characters.avatar_r2_path` to null (DB update)
4. Synchronously delete the R2 object after the DB update succeeds

#### Scenario: Successful deletion with existing avatar
- **WHEN** an authenticated user sends `DELETE /characters/:id/avatar` and the character has an `avatar_r2_path`
- **THEN** the system returns 204, `avatar_r2_path` is null on the character, and the R2 object is deleted from storage

#### Scenario: Idempotent when no avatar exists
- **WHEN** an authenticated user sends `DELETE /characters/:id/avatar` and `avatar_r2_path` is already null
- **THEN** the system returns 204 and no storage operation is performed

#### Scenario: Character not found or not owned
- **WHEN** an authenticated user sends `DELETE /characters/:id/avatar` for a character that does not exist or belongs to another user
- **THEN** the system returns 404

#### Scenario: Invalid character UUID path param
- **WHEN** an authenticated user sends `DELETE /characters/:id/avatar` with a non-UUID `:id`
- **THEN** the system returns 400

---

### Requirement: Stale pending avatar upload cleanup
The system SHALL periodically delete `pending_character_avatar_uploads` rows older than the presign TTL (15 minutes) and delete their corresponding R2 objects. This prevents orphaned pending records and unclaimed R2 objects from accumulating.

#### Scenario: Stale pending rows and R2 objects are purged
- **WHEN** the stale avatar upload cleanup job runs
- **THEN** all `pending_character_avatar_uploads` rows with `created_at` older than 15 minutes are deleted, and their R2 objects are deleted from storage
